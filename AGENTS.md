# A River Becoming: rules for every agent

This is the one rulebook for every agent on this repo: Claude Code or Codex, on Gavin's Mac mini, on Will's machine, on bitcube, or the studio agent behind mission control. `CLAUDE.md` only points here.

The repo is **github.com/gavaiken/river-bitcube**. It runs the installation on **bitcube**, the Windows mini PC that drives it (at Gray Area now), where it is checked out at `C:\Users\user\River\river-bitcube`. Next to that checkout, `C:\Users\user\River\river-agent` is Dave's repo **github.com/drocamor/river-agent** (the Modal agent; merges to its main deploy to Modal). The parent `C:\Users\user\River` is not a repo; it is shared over SMB as `\\bitcube\River`.

## Start here, every session
1. **`git pull`.** Never start work on an old checkout.
2. **Read [`HANDOFF.md`](HANDOFF.md)**: who had the baton last, when, where things stand, what's next. It is the one current "where we are".
3. **Take the baton.** If `HANDOFF.md`'s `Updated` time is less than **30 minutes** ago and it names someone other than the person you're working for (Gavin, Will, the studio agent), ask your person first: "Will's agent was working 12 minutes ago. Take the baton anyway?" No lock, just that question. Then set **Holder**, **Where** (repo only, or bitcube) and **Updated** in `HANDOFF.md`, commit and push before anything else. Only one agent works **on bitcube** at a time; the baton is how you know.
4. **Work** in small commits on `main`. `git pull --rebase` before each commit (the mini, bitcube, Will and the studio agent all push here), run `tools/check` before each push, and check `git push`'s exit code.
5. **Hand off before you stop:** rewrite `HANDOFF.md` (state, what changed, what's next, anything half-done: there should be nothing half-done) and append a SESSION SUMMARY to `docs/sessions/<name>.md`, then push. A session that stops without a pushed handoff leaves the next one blind.

## What you must not break
Everything else is open: iterate freely.
- **The default show** (the boot file: `River\boot-file.txt` on bitcube, else `shows.json` `boot_default`): what opens when bitcube restarts. Never edit a show file in place to try an idea; make your own. Switching shows never changes the default; any show can be made the default with mission control's **Set as default**, a separate, deliberate action (an agent does it only when its person asks).
- **The show's calibration and mapping:** the LED map and screen positions each show pins in `shows.json` (`tools/pixelmap/*.json`), the rope addressing in Will's `RopeLights\config.local.json`, the screens module. A new calibration is a new dated file pinned only by your own show; never re-pin someone else's show.
- **Mission control** (`mission/`): it updates itself from `main` within about 5 minutes, so a broken push reaches the team's phones fast. `tools/check` must pass first.
- **Secrets:** this repo is public. See Rules.

Copy it with `tools\td_save.ps1 -Target river-<name>.toe`, give it its own build script `td/build/build_<name>.py`, and add it to `shows.json` with `kind: "viz"`.
- File names never change after creation. Who made it, who edited it last, when and what changed live in its `shows.json` entry, together with a description of at most 100 words (what it's meant to do, its inputs). Mission control shows these before anyone switches to it, so keep them true: `tools/check` refuses a change to a show file or its build script that doesn't update its entry.
- Mission control's "What's showing" card switches to any offered show (after showing its description), "Back to default" returns to the default show, and "Set as default" changes what opens at restart.
- Registry format and tooling: [`docs/shows.md`](docs/shows.md). Going back to a known-good point: [`docs/checkpoints.md`](docs/checkpoints.md).

**Where you're running.** On bitcube, the paths here are local. Anywhere else (Gavin's Mac mini, Will's laptop), reach bitcube with `ssh bitcube` (on Will's tailnet `bitcube.tail03bc1a.ts.net`, user `user`, key auth) and run its PowerShell tools there (`tools/mini/bitcube_ps.sh` from a Mac); TouchDesigner work happens on bitcube through the bridge (`tools\td.ps1`). Pure repo work (docs, mission control, tests) needs no bitcube.

Background docs (read when you need them): `docs/a-river-becoming-hardware.md` (verified hardware: LED ropes, PSAC10 Art-Net boxes, rack controller, HUB75 panels), `docs/a-river-becoming-notes.md` (design notes from the team meetings), `docs/show-files.md` + `docs/files/*.md` (one page per show file), `GLOSSARY.md` (the agreed terms: use them), `docs/system/system.json` (every machine, IP, port, account and connection; [interactive map](https://gavaiken.github.io/river-bitcube/system/); when you change any of them, update it, run `python tools/system_docs.py` and the tests in `tools/tests`). ## TouchDesigner gotchas (learned the hard way)
- **Anything modal in TD freezes the bridge.** A dialog blocks TD's main thread, so `td.ps1` calls hang. `td.ps1` times out after 20 s and names the blocking dialog. Someone then has to answer it on the console (VNC), or Claude clicks it after taking a screenshot.
- **Show files:** see "Show files and their pages" above. The online file's rain/river field is `td/build/build_river_local.py` (map from `tools/pixelmap/`). `td_save.ps1` saves whichever file is open; `-Target x.toe` does a Save As.
- **Never light all ropes white at once:** a full-white box draws about 1.5 kW (PSAC10 boxes are rated 1,750 W, each with its own breaker), so both boxes at full white (~3 kW) would trip a shared wall circuit. `Boxwatts` (600 W per box) is **our own software limit** in `artnet_out.py` (D13), not a hardware limiter; rope max brightness is 1.0 (Gavin, 27 Oct). Plain Gray-code patterns are *not* balanced (rope bit 4's inverse lights every rope of box 1), so `tools/pixelmap/capture.py` dims each pattern pair until no box draws more than half its power at the cap (`graycode.pattern_brightness`, at most 300 W/box).
- **Save only with `.\tools\td_save.ps1`.** Never call `project.save(...)` directly. TD's incremental save (pref `general.inc`, default 2) made a named save collide with an existing `river.N.toe` and prompt "already exists. Replace?". On bitcube `general.inc` is now 0. `td_save.ps1` re-checks it, refuses to save if it's back on, verifies `river.toe`'s timestamp, and deletes stray `river.N.toe`.
- **Never put unpicklable objects (sockets, files) in `comp.storage`.** TD pickles storage into the `.toe` on save, and a socket triggers a modal "saved with errors". Keep live objects in a holder module in `sys.modules`, as `td/ropes/artnet_out.py` does.
- **Save before cooking a new GLSL shader.** A shader that sampled an unwired input hung the Iris Xe driver (TDR) and killed TD. Index `sTD2DInputs[]` with literal constants only, guarded by `TD_NUM_2D_INPUTS`. In multi-input TOPs a new input connector only appears on the next frame (see `wire()` in `td/build/build_panels.py`).
- **Changes live in the repo, not only in the `.toe`.** The rope/panel logic and shaders are files synced into DATs. `td/build/*.py` rebuild the COMPs idempotently: `.\tools\td.ps1 -File .\td\build\build_ropes.py`. From Git Bash, run PowerShell scripts with `powershell -ExecutionPolicy Bypass -File ...`.
- **`absTime` restarts at 0 when a project loads, but `comp.storage` is saved in the `.toe`.** Never compare `absTime` with a time kept in storage without handling the clock going backwards. The rope sender stalled after a reload this way (fixed 18 Oct in `artnet_out.tick`).
- **Non-Commercial key: TOPs max 1280×1280.** The full-screen black for the LED display comes from a Container COMP (`panels/screen`), not a TOP. Panel `y` counts up from the bottom.
- **Live camera video in TD: never use a Video Stream In TOP** (creating one through the bridge froze TD's main thread, 19 Oct). Use `td/cameras/river_cam.py`: TD starts a relay process (`python river_cam.py relay <cam> <stream> <td-pid>`) that runs ffmpeg and writes each newest RGBA frame (already `vflip`ped) into named shared memory `river_cam_<cam>_<stream>`; a Script TOP copies it in onCook. The relay exits when TD does. A reader *thread* inside TD only got ~2 fps; the relay keeps the camera's full 10 fps.
- **Time Machine TOP needs a Texture 3D TOP (2D array) as input,** not a Cache TOP ("Input texture must be a 3D or a 2D Array"). Cache Select TOP does take a Cache TOP. Used in `river_local`'s "river memory" (`cam_t3d` → `cam_memory`).
- **bitcube pushes can be rejected silently** if another machine pushed meanwhile: `git pull --rebase --autostash` before committing, and check `git push`'s exit code.
- **Never pass `copyNumpyArray` a non-contiguous view** (e.g. `np.flipud(...)`): that froze TD. Use a contiguous copy.
- **`.toe` files are compressed:** grepping the raw bytes proves nothing. To check a show file for secrets, unpack it with `C:\Program Files\Derivative\TouchDesigner\bin\toeexpand.exe` and scan the parts. Camera URLs are read from `secrets.local.json` at run time and never stored in a parameter.
- **Modal link (20 Oct):** `tools/modal/modal_link.py` (Startup: `Start-Modal.cmd`; status: `.venv\Scripts\python.exe tools\modal\modal_link.py status`; logs `River\logs\modal-*.log`) runs Dave's `capture.py` for both cams (sub-stream, RTSP over TCP) and `sync.py` (mirror in `River\gallery_state`, served on 8770). A second copy exits at once; children die with the supervisor. Started from SSH it dies with the session: launch `Start-Modal.cmd` through a one-off interactive scheduled task. In TD, `td/modal/modal_scene.py` scales river_local's look from the scene (Modal page `Modalmix` 0 = off). `secrets.local.json` holds only secrets: `tools/tests` treats every value in it as one, so a public URL in it fails the secret scan.
- **Copying a TD operator keeps its parameter binds.** `modal_canvas` was copied from Andi's Web Render, whose url, resolution and reload were *bound* to its parent's custom parameters: setting `.val` did nothing and the binds errored. Unbind (`p.bindExpr = ''`, `p.mode = ParMode.CONSTANT`) after a copy. Copying a Web Render (inactive) and switching it on a moment later did not freeze TD.
- **A camera relay can hang on a dead link.** On 19 Oct the river cam dropped overnight and ffmpeg sat on the dead TCP connection for 11 h (TD stayed on the rain). `river_cam.py` now passes `-timeout` and its watchdog kills ffmpeg after 20 s without a frame.
- **Lights switched off ≠ sender off.** A network error (boxes powered down, cable pulled, lighting NIC lost `2.0.0.8`) makes `artnet_out.tick` back off and retry every 2 s (`status()['retrying']`); it never turns `Active` off for those, so the ropes pick the rain up again by themselves when powered back on. Only a non-network error (a bug, a bad config) still switches `Active` off. Tests: `tools/tests/test_artnet_retry.py`.
- **Dark ropes = keep sending black.** When Art-Net stops, the lighting hardware plays its own colour-cycling program (rack SD card or PSAC10 PLAY mode). To keep the ropes dark, use `Source='black'` with `Active` on, never `Active` off.
- **Displays (2026-10-18):** Windows extends the desktop across two displays. `M14` (USB-C, Lenovo, 1366×768, **primary**, at 0,767) and `LED 1920X108…` (the Colorlight sender for the HUB75, `DISPLAY2`, 1920×1080 at 1366,767). TD's `monitors` lists both. The panels window used to anchor to the primary display, so it landed on the M14: find the LED monitor by name instead (plan item B). Keep the M14 as primary so the desktop and taskbar stay off the panels.
- **Booting (fixed and verified by a restart, 2026-10-18 12:27):** the UEFI boot order now puts Windows Boot Manager ahead of Ubuntu/GRUB (`bcdedit /set {fwbootmgr} displayorder {bootmgr} /addfirst`). Ubuntu is still installed and can be picked from the firmware boot menu. Auto-login uses Sysinternals Autologon: the password is stored as an LSA secret, not plain text in the registry, and Windows' Hello-only sign-in (`DevicePasswordLessBuildVersion`) is off. Tailscale runs unattended (connects before login), and sleep and hibernate on AC are both off. A restart takes about a minute end to end.
